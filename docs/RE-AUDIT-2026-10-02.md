Homepage image transfer 849 → 478 KB.
- **Below-fold scene chunks prefetch on first interaction (`f2e5780`):** the idle prefetch was first removed (`c6be981`) to clear the ~103 KB Lighthouse flagged 100 % unused at first paint, but that took the scene chunks off every path — an abrupt jump to the Shield/Finale act then met an empty canvas while the chunk downloaded. Replaced with `usePrefetchOnInteraction`: the chunks download on the visitor's **first scroll/wheel/touch/pointer/key**, so a bounce visit downloads nothing while anyone who scrolls starts the fetch thousands of px early. Verified live: 0 scene chunks at idle-at-top; 3 scene chunks fetched on first scroll; canvas mount gating still correct (2 at load → `#platform` 1 → `#finale` 1); 0 page/console errors. **Caveat:** mount-latency figures on this box are unusable (same event measured 1.3 s and 10.7 s across runs at 100 % CPU) — the earlier "regression" reading was inside this machine's noise, not a verified product regression.
- **GTM deferred off the critical path (`bfcc353`):** the inline snippet still ships in the server HTML (Tag Assistant/install check intact) but now injects `gtm.js` only on **idle after load, or first user interaction**. GTM + GA4 (~305 KB) no longer run inside the load window. GA4 still fires — verified live: `gtag.js` @ ~8.2 s, **2 collect beacons**. Early `lib/analytics.ts` `trackEvent()` calls queue in `dataLayer` and flush on load — **no events lost**. (`NEXT_PUBLIC_GA_ID` is *not* set in Vercel; the 177 KB `gtag/js` is loaded by the GTM container's own GA4 tag — correct architecture, no redundancy to remove.)

## 13. Homepage diagnosis — why PSI fails, and the culprit list

Profiled the live homepage (mobile emulation, Google-throttled settings not available locally, so absolute values are inflated by this 100 %-CPU box — the **contrast and ranking** are the reliable part).

**It is not a network problem.** 46 requests, network settles at **5.9 s**; no polling/infinite requests.

**LCP is main-thread-bound, not asset-bound.** LCP element = the **logo image** (`/_next/image?url=%2Fsgc-logo.png&w=384&q=75`). LCP breakdown: TTFB 244 ms / load delay 729 ms / transfer 63 ms / **element render delay 2,558 ms** — the image is ready but cannot paint.

**Load-time script eval is the top cost.** `mainthread-work-breakdown`: Script Evaluation **12,453 ms** (vs Style & Layout 2,872 ms). Largest long tasks at load:

| Long task | Source |
|---|---|
| 3,422 ms | `110q6k5sdl4es.js` — **motion library** |
| 2,109 ms | `133c44ripyune.js` — **GSAP** |
| 1,254 ms | `110q6k5sdl4es.js` — **motion** again |
| 762 + 498 ms | `0xj…js` — three.js |
| 588 ms | `gtag.js` (now deferred) |

**Runtime cost is the visible hero scene, not off-screen waste.** Measured in one session:

| Condition | Long tasks | rAF frames/s |
|---|---|---|
| At top — hero visible | **32 in 6.2 s** | **5/s** — every hero frame exceeds 50 ms |
| At bottom (scrollY 40,798) — hero far off-screen | 1 in 6.8 s | 45/s — healthy |

So the hero 3D scene's per-frame work saturates the main thread while visible; once scrolled past, the thread recovers. That sustained load is what keeps LCP rendering late and is the most likely reason PSI never reaches a quiet state and returns 500.

**Conclusion — two distinct, separately fixable costs:**
1. **Hero per-frame render cost** (Bloom/`EffectComposer` post-pass + high `dpr` + particle count) → saturates the main thread while visible; blocks LCP paint.
2. **Load-time evaluation of two animation libraries** (motion ≈4.7 s of long tasks, GSAP ≈2.1 s) → the TBT floor at load.

Both are on the homepage only; content pages have neither.
